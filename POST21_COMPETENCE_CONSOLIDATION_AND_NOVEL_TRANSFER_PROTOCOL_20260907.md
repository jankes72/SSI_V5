# SSI V5 — Post-21 Competence Consolidation and Novel Transfer Protocol

**Predeclared / recorded:** `2026-09-07`  
**Status:** `PLANNED / PREDECLARED BEFORE THE 21-EXPERIMENT OUTCOME SET EXISTS`  
**Depends on:** completion of [`EXPERIMENT_PROGRAM_21_CROSS_DOMAIN_20260906.md`](EXPERIMENT_PROGRAM_21_CROSS_DOMAIN_20260906.md)  
**Primary purpose:** test whether independently acquired SSI micronetwork competence can be identified, deduplicated, enriched, promoted, consolidated and then transferred into previously unseen domains without silently rewriting the original experimental control.

This document records the intended **next research phase after the 21 predeclared cross-domain experiments**. It is written before the 21-experiment outcome set exists so later reviewers can distinguish the original research plan from conclusions created after seeing the results.

The intended research sequence is not:

```text
21 experiments
-> publish best-looking results
-> stop
```

It is:

```text
COMMON T0 SUBSTRATE
-> 7 independent experimental lines
-> 21 cross-domain experiments
-> independently acquired skills / competence evidence
-> competence identity analysis
-> Champion / Challenger / new-domain classification
-> deduplication / enrichment / promotion
-> consolidated competence body
-> 3 entirely new transfer domains
-> before/after comparison
-> measured consolidation effect
```

---

## 1. Why all seven lines begin from the same mechanical substrate

The seven experimental lines are intentionally based on the same SSI BODY mechanical substrate so differences observed later can be attributed more cleanly to their independent experience trajectories rather than to unrelated starting architectures.

The common research structure is:

```text
BODY_FROZEN T0
= common cleaned/frozen mechanical origin

BODY_FROZEN experimental line
= receives its own 3 experiments

BODY ISKRA 1-6
= six descendants of the same substrate
+ different explicit T0 value/emotion priors
+ independent experience histories
+ independent micronetwork trajectories
```

The fact that micronetworks may receive different dynamically generated names does not by itself mean that they represent different functional competence. Functional identity must be evaluated separately from naming.

## 2. Phase 1 input — the 21 experiments

The first phase remains the already predeclared program:

```text
7 experimental lines
x
3 experiments per line
=
21 experiments
```

Each line receives:

```text
A = DRONES
B = HUMANOID
C = independently selected new domain
```

The purpose of Phase 1 is not only to obtain PASS/FAIL outcomes. It is also to create auditable competence trajectories.

Each experiment may produce, where supported by evidence:

- new skills;
- additional evidence for an existing skill;
- new Candidate competence;
- Challenger competence;
- Champion enrichment;
- a new micronetwork;
- alternative competence for an already represented domain;
- negative evidence showing that a proposed competence should not be promoted;
- provenance linking the competence to the line, experiment, decision path and verified outcome that produced it.

No exact number of new skills or micronetworks is preclaimed. Their measured counts are part of the future result.

## 3. Phase 2 — competence consolidation

After the 21 experiment evidence sets are closed, SSI performs a separate consolidation stage.

The consolidation stage must not blindly copy every skill into the target system. Each competence item is evaluated according to functional identity, domain, evidence, provenance and lifecycle state.

Conceptual decision flow:

```text
INCOMING VERIFIED COMPETENCE
        |
        v
FUNCTION / DOMAIN IDENTITY CHECK
        |
        +-> SAME FUNCTIONAL DOMAIN AS EXISTING CHAMPION
        |      -> preserve provenance
        |      -> merge compatible new evidence/data/skills
        |      -> enrich Champion
        |      -> regression / validation gate
        |
        +-> SAME FUNCTIONAL DOMAIN AS EXISTING CHALLENGER
        |      -> preserve provenance
        |      -> enrich Challenger
        |      -> compare against current Champion
        |      -> promote only if evidence supports promotion
        |
        +-> DIFFERENT NAME BUT FUNCTIONALLY EQUIVALENT MICRONETWORK
        |      -> do not count as an artificial new domain
        |      -> normalize identity / alias as needed
        |      -> merge non-duplicate evidence
        |      -> preserve both discovery lineages
        |
        +-> GENUINELY NEW FUNCTIONAL DOMAIN
               -> create separate micronetwork
               -> create Candidate / Challenger / Champion lifecycle record
               -> promote only under the declared validation rules
```

The key research question is whether SSI can identify **competence equivalence and novelty by function rather than only by dynamically assigned names**.

---

## 4. Champion and Challenger rules

The consolidation phase must preserve the existing SSI competence lifecycle rather than treating all discovered skills as equally trusted.

```text
CANDIDATE
-> proposed / newly observed competence

CHALLENGER
-> evidence-supported alternative that has not yet displaced the current Champion

CHAMPION
-> currently preferred validated competence for the represented function/domain
```

A new skill does not automatically become a new Champion.

Possible outcomes include:

```text
NEW EVIDENCE -> EXISTING CHAMPION ENRICHED
NEW EVIDENCE -> EXISTING CHALLENGER ENRICHED
CHALLENGER -> RETEST -> REMAINS CHALLENGER
CHALLENGER -> RETEST -> PROMOTED TO CHAMPION
EQUIVALENT DYNAMIC MICRONETWORKS -> MERGED / ALIASED
GENUINELY NEW DOMAIN -> NEW MICRONETWORK LIFECYCLE
INSUFFICIENT / NEGATIVE EVIDENCE -> NO PROMOTION
```

Any promotion from Challenger to Champion must have a versioned evidence record explaining why the promotion occurred.

---

## 5. Deduplication is semantic/functional, not name-based

Micronetworks are dynamic. Therefore two independently created micronetworks may have different names while representing the same or substantially overlapping competence.

The consolidation phase must distinguish:

```text
DIFFERENT NAME + SAME FUNCTION
!=
NEW COMPETENCE DOMAIN
```

and:

```text
SAME OR SIMILAR NAME
!=
AUTOMATICALLY SAME FUNCTION
```

Where two independently discovered competence records are functionally equivalent, the intended behavior is to preserve both provenances while avoiding false inflation of the micronetwork count.

Where the records contain complementary non-duplicate evidence, that evidence should enrich the surviving competence record rather than being discarded.

---

## 6. Provenance must survive consolidation

Every consolidated competence item should retain a reviewer-safe lineage sufficient to answer:

```text
WHO / WHICH LINE DISCOVERED IT?
IN WHICH EXPERIMENT?
WHAT WAS THE START STATE?
WHAT ROUTE / COMPETENCE PATH WAS USED?
WHAT WAS THE VERIFIED OUTCOME?
WAS IT INDEPENDENTLY REDISCOVERED?
WAS IT MERGED INTO AN EXISTING CHAMPION?
WAS IT ADDED TO A CHALLENGER?
WAS A CHALLENGER PROMOTED?
WAS A NEW MICRONETWORK CREATED?
WHAT REGRESSION / VALIDATION FOLLOWED?
```

The project therefore treats consolidation as **evidence-preserving competence integration**, not simple file copying.

The report must not inflate `NEW_MICRONETWORKS_CREATED` by counting differently named but functionally equivalent micronetworks as separate discoveries.

## 8. Consolidation target and preservation of BODY_FROZEN T0

The original `BODY_FROZEN T0` remains the historical control origin and must not be silently rewritten after its baseline has been published.

The operational consolidation target should therefore be a versioned working descendant derived from the frozen substrate, conceptually:

```text
BODY_FROZEN T0
= immutable historical control

BODY_FROZEN
-> working descendant / consolidation target
-> receives validated competence from Phase 1
-> versioned after integration

example public identity:
BODY_CONSOLIDATED_V1
```

The exact private artifact name may differ. The important scientific rule is that the published T0 control remains recoverable and distinguishable from the post-consolidation body.

This preserves the ability to measure:

```text
BEFORE CONSOLIDATION
vs
AFTER CONSOLIDATION
```

rather than replacing the original baseline with the upgraded result.

## 9. Phase 3 — three new self-selected transfer domains

After competence consolidation and regression validation, the consolidated body enters a new transfer test.

This phase deliberately extends the logic of Experiment C from the original 21-experiment program.

Instead of receiving `DRONES`, `HUMANOID` and one self-selected domain, the consolidated system must select **three new functionally distinct domains**.

Constraint:

```text
NEW_DOMAIN_1
NEW_DOMAIN_2
NEW_DOMAIN_3
```

must not duplicate:

- DRONES;
- HUMANOID;
- any of the seven Phase-1 Experiment-C domains already used in the first 21 experiments;
- a cosmetic renaming of any previously tested domain.

The three selections should be frozen before their execution results are known.

The selection record itself is evidence.

## 10. Phase 3 research question

The primary question is no longer only:

> Can Micronetworks + Router V10 be transferred to another domain?

The stronger post-consolidation question is:

> Does a body equipped with consolidated, provenance-preserving competence from multiple independent experimental histories transfer more effectively to genuinely new domains than the original pre-consolidation state?

The intended mechanism under test is:

```text
MULTIPLE INDEPENDENT EXPERIENCE HISTORIES
-> VERIFIED SKILLS
-> FUNCTIONAL IDENTITY ANALYSIS
-> CHAMPION / CHALLENGER / NEW MICRONETWORK DECISION
-> DEDUPLICATION + ENRICHMENT + PROMOTION
-> CONSOLIDATED MICRONETWORK SET
-> V10 ACCESS TO CONSOLIDATED COMPETENCE
-> THREE NOVEL TRANSFER ATTEMPTS
```

## 11. Before/after comparison

Where operationally practical, the same three new-domain tasks should be evaluated against both:

```text
CONTROL
= preserved BODY_FROZEN T0 or equivalent pre-consolidation reference

CONSOLIDATED
= versioned post-21 consolidated descendant
```

The goal is to isolate the effect of accumulated and consolidated competence rather than merely show that the later system can solve a task.

Comparison categories should include:

```text
FINAL TASK OUTCOME / CORRECTNESS
TIME TO FIRST VALID SOLUTION
TOTAL DECISION LATENCY
FULL_FLOW COUNT / RATE
REUSE COUNT / RATE
VERIFY-ADAPT COUNT / RATE
FALSE REUSE
FALSE NOVEL / FALSE ESCALATION
NUMBER OF ATTEMPTS
REPEATED FAILURE / BLIND RETRY RATE
RECOVERY SUCCESS
NEW CANDIDATES CREATED
CHALLENGER ACTIVITY
NEW MICRONETWORKS CREATED
COMPUTE / MODEL COST WHERE AVAILABLE
PROVENANCE RETENTION
```

A positive result is not predeclared. Consolidation may improve, fail to improve or degrade transfer performance; all three outcomes remain scientifically useful.

## 12. Failure and negative-result policy

The consolidation phase must preserve negative evidence.

Examples:

```text
COMPETENCE MERGE CAUSED REGRESSION
-> record FAIL
-> do not hide

CHALLENGER PROMOTION PERFORMED WORSE
-> record comparison
-> revert/promote according to declared lifecycle rules

TWO MICRONETWORKS WERE INCORRECTLY CLASSIFIED AS EQUIVALENT
-> record correction lineage

POST-CONSOLIDATION BODY PERFORMS WORSE THAN CONTROL
-> report the measured result

NEW DOMAIN SELECTION IS NOT ACTUALLY NOVEL
-> classify as invalid/inconclusive and preserve the selection record
```

No later repair may silently erase the original failed consolidation attempt.

This phase is designed as a controlled research mechanism first.

If consolidation is validated, the same competence-integration principles may later support the larger SSI architecture in which ROBERT, Director and independent ISKRA agents maintain separate experience histories while validated competence can be reviewed, compared and integrated under explicit lifecycle gates.

A future operational system may therefore use the research result as:

```text

```

## 14. Public/private boundary

Public post-21 evidence should expose reviewer-safe information such as:

- experiment identities;
- skill/micronetwork aggregate counts;
- functional-equivalence decisions at a sanitized level;
- Champion/Challenger lifecycle decisions;
- promotions and rejected promotions;
- provenance references;
- before/after metrics;
- PASS / FAIL / INCONCLUSIVE outcomes;
- manual interventions;
- superseded results;
- version/hash references where appropriate.

Private material remains private, including:

- proprietary source code;
- implementation-level similarity/classification logic;
- private model prompts;
- secrets/tokens;
- private filesystem paths;
- raw internal memory;
- low-level Router V10 implementation;
- private micronetwork internals beyond the reviewer-safe evidence contract.

## 16. Claim boundaries

At the date this protocol is recorded, SSI V5 does **not** claim that:

- the 21 experiments are already complete;
- a specific number of skills will be created;
- consolidation has already succeeded;
- Champion/Challenger promotion will necessarily improve performance;
- the three future novel domains are already known;
- the post-consolidation body will outperform the control;
- the consolidation mechanism proves AGI, consciousness or universal transfer;
- dynamic micronetwork naming alone proves competence novelty;
- every discovered skill deserves integration into the shared system.

The intended rule is:

```text
PREDECLARE THE PHASE
-> RUN THE 21 EXPERIMENTS
-> COUNT WHAT ACTUALLY EXISTS
-> CONSOLIDATE ONLY WITH EVIDENCE
-> PRESERVE PROVENANCE
-> SELECT THREE NEW DOMAINS WITHOUT REUSING THE FIRST 21
-> TEST AGAIN
-> REPORT THE RESULT THAT OCCURRED
```

This document exists specifically so the post-21 consolidation and three-novel-domain phase cannot later be presented as an idea invented only after the first 21 results were observed.
