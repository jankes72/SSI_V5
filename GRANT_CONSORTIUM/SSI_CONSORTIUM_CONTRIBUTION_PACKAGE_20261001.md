## Proposed SSI contribution

SSI V5 can be positioned as an evidence-oriented agentic-AI subsystem and research method rather than as a finished robotics product.

### Core contribution

```text
PERSISTENT MULTI-AGENT RUNTIME
+ VERSIONED COMPETENCE / MEMORY
+ ADAPTIVE ROUTING
+ FROZEN EVALUATION
+ CROSS-AGENT CONSULTATION / CONSOLIDATION
+ ROLLBACK / RECOVERY
+ CZARA HUMAN-AI RESEARCH LAYER
+ LAB / EVIDENCE / PROVENANCE
```

### Candidate project use

A consortium can use SSI for controlled research on:

- continual and lifelong competence acquisition;
- reuse versus deeper reasoning;
- multi-agent coordination;
- human expert feedback and revision lineage;
- robustness under missing/changed information;
- cross-domain transfer;
- auditability and reproducibility;
- offline or degraded-connectivity autonomy in controlled scenarios;
- robotics and multi-robot task planning through partner-owned simulators or hardware.

## Proposed role split

| Role | SSI side | External partner side |
|---|---|---|
| Architecture | SSI integration boundary, agent/evidence architecture | independent review and target-system constraints |
| Benchmark design | acceptance-contract tooling | unseen tasks, domain criteria, baselines |
| Software experiments | execution, logging, replay, rollback | reference environment / comparator |
| Robotics | software-side interface and policies | simulator, robot hardware, safety envelope, operators |
| Domain expertise | translate requirements into bounded contracts | validate realism and operational relevance |
| Scientific validation | publish run evidence | independent analysis / replication |
| Exploitation | SSI IP / integration route | domain deployment, productization, user access |

## Proposed consortium outcomes

A realistic project should aim to produce evidence beyond the current internal level:

1. frozen multi-partner benchmark specification;
2. baseline comparison against agreed alternatives;
3. independent execution or replication;
4. simulation/digital-twin validation;
5. target-specific physical pilot where safe and relevant;
6. safety/security assessment;
7. reproducibility package;
8. exploitation-ready integration boundary.

## Partner acceptance model

The recommended first technical engagement is small:

```text
PARTNER INPUT
= one previously unseen bounded task family

BEFORE RUN
= acceptance criteria + baseline + version frozen

DURING RUN
= no hidden result rewriting

AFTER RUN
= PASS / FAIL / INCONCLUSIVE
+ timings
+ provenance
+ failure analysis
+ optional learning/consolidation
+ frozen re-test
```

This allows a potential partner to test the method without first accepting the full SSI architecture.

## Due-diligence questions SSI is ready to answer

A partner should be able to ask:

- What exact claim is being tested?
- Which SSI version is used?
- What is frozen before the run?
- What can learn during training and what cannot learn during validation?
- Where are FAIL and INCONCLUSIVE records retained?
- What is public and what is proprietary?
- Which outcomes are internal only?
- Which results have been independently replicated?
- What is required to move from software lab to physical validation?
- Who owns background and newly created foreground?
